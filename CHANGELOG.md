### Added

- **`feat/daemon-discovery-scheduler` — closes the operator-path loop.** The daemon now runs `DiscoveryOrchestrator.scan(trigger="scheduled")` 60s after `--start` and every 24h thereafter (with a 1h backoff on transient failures). A fresh-machine daemon start populates the Assets tab without any manual CLI invocation. Closes the fourth shipped-but-dormant gap of v0.2.2 (after mappers → scoring → daemon-cadence → CLI-persistence). Three R1 cadence constants — `DISCOVERY_STARTUP_DELAY = 60s`, `DISCOVERY_CADENCE = 24h`, `DISCOVERY_FAILURE_BACKOFF = 1h` — judge AUTO-RATIFY per CONTRACT §5a/§6a (Rajan pre-signal 2026-06-12). Loop body lives in the new `src/claude_monitoring/discovery_scheduler.py` module (87 LOC) so it doesn't bloat `monitor.py`; thread launched from `start_monitoring()` as `DiscoveryScheduler`. P4.5 (background scheduler) will collapse the constants into a `schedule.toml`-driven config — no configurability promised in v0.2.2.
  - **In-flight-marker handling: wires the merged `audit.finalize_crashed_runs` (P1.5, dormant until now — the SIXTH shipped-but-dormant gap).** A daemon SIGKILLed mid-scan leaves `discovery_runs.completed_at = NULL` forever, which would surface a permanent "Scan running…" banner in the new envelope field below. Fix: `start_monitoring()` calls `attack_surface.orchestrator.audit.finalize_crashed_runs(conn)` BEFORE the scheduler thread launches. The function uses a 600s cutoff docstring-paired with `ScanLock.STALE_THRESHOLD_SEC` so stale lock + unfinished audit row reflect the same crashed-scan event, and sets `status="crashed"` + `finalized_at_daemon_startup=True` in the errors JSON so crash never becomes indistinguishable from clean completion. **Judge phase-a.a1 verdict 2026-06-12 caught my first-pass duplicate that re-implemented this with the wrong contract** (raw 4h UPDATE missing the crashed-status marker, breaking ScanLock consistency, with an operator-visible inversion at restart-after-1h-crash). Memory `project_shipped_but_dormant_pattern.md` updated to record that the architect-pass also missed it; only the judge's independent line-by-line read against merged main caught the dormant duplicate.
  - **`/api/assets` envelope adds `scan_in_progress`.** Sourced from `discovery_runs.completed_at IS NULL`. Dashboard renders "Scan running… (Xs in, trigger: scheduled)" instead of "No assets" when applicable — operator must never see "no assets" while a scan is grinding. Four-case truth table: rows × in-flight = empty+null/empty+inflight/populated+null/populated+inflight; rendered distinctly.
  - **CLI persistence becomes the default.** `python -m claude_monitoring.attack_surface.cli scan` now writes results to the live monitor DB. `--no-persist` preserves the legacy throwaway behavior for development debugging where touching the live DB is undesirable.   - **§9.1.1 polling-cadence closeout (Rider 1).** Replaces the "never" prose in P4.2's amendment with the shipped cadence (60s startup delay → 24h periodic). The §9.1.1 gap P4.2 deferred to "P4.5's responsibility" closes here, with the proviso that P4.5 will adopt the constants as schema defaults.
  - **13 new tests** (`tests/test_daemon_discovery_scheduler.py`): scheduler timing (startup delay, periodic cadence, backoff inside-try-not-finally pin), persistence-via-conn, thread launch in `start_monitoring()`, CLI default + `--no-persist` pair, envelope tri-case (idle / in-flight / completed), same-process lock contention, startup-sweep clears-stale + leaves-recent.
  - **Architect-pass MINOR (folded in-scope):** all four lifecycle edges named by Rajan came back clean (thread shutdown, watchdog interaction, single-instance guard, scan-lock contention). The one BLOCKING-then-folded finding was the stale-NULL sweep — promoted from "carry-forward one-liner" to in-PR scope because shipping the envelope without it makes the field wrong by design after any daemon crash.
  - **SQLite busy_timeout bumped 5s → 30s (operator-path demo finding, 2026-06-13).** The first end-to-end demo against a live daemon revealed the scheduler's persist (1094 UPSERTs in one transaction) colliding with the live JSONLSessionWatcher's writer. ### Documented

- **P4.2 CVE-cache conformance — spec §9.1.1 amendment.** Ratified Rajan 2026-06-11. Names two intentional divergences between spec §9.1 + directive line 191 and the shipped implementation: (1) **storage shape** — PR #114 ships file-backed caches (`querybatch/<hash>.json` 24h symmetric TTL, `vulns/<vuln_id>.json` 7d TTL, chmod 600, atomic tempfile+rename) under `${VIGIL_OUTPUT}/cves/` instead of the relational `cve_cache` + `asset_cves` tables. Per-asset CVE data is materialized inline as `assets.risk_factors.cves` JSON via the §6.10 v1 schema. Tables stay DDL'd by P0.2 migrations and reserved for v0.3+ SQL consumers (reverse-CVE queries, severity histograms) without a schema-breaking migration. Rationale: privacy-posture isolation (CVE query metadata kept out of `monitor.db` blast radius); simpler TTL semantics (file mtime IS `fetched_at`); per-entry corruption isolation; no JOIN needed for v0.2.2 consumers. **(2) polling cadence** — the daemon does NOT periodically invoke the orchestrator. Verified `grep -rn "DiscoveryOrchestrator\|orchestrator\.scan" src/` returns one production caller, `attack_surface/cli.py:64`. The 24h TTL only kicks in on operator-triggered scans (CLI or dashboard); idle machines silently age past 24h. **Polling-cadence half of the contract is explicitly P4.5's responsibility** (directive §3 line 194: "Background scheduler. Daily discovery scan + daily CVE poll. Configurable schedule per spec §8.2"). Flagged so the v0.2.2 release-readiness note states "CVE freshness is scan-triggered" honestly rather than implying daemon-side polling exists. Inline comment blocks added above the two DDL'd-but-empty tables in `persistence/migrations.py` so future contributors don't reverse-engineer them as "forgotten." Naming reconciliation ratified: `cve_references` (the column name in migrations) is canonical, replacing spec's `references` which is a reserved SQL keyword that fails to parse.

### Known limitations

- **Browser-extension risk band capped at HIGH (without CVE feed evidence).** Per §6.1 four-factor weights + §6.2 max-wins rule composition, a Chrome / Edge / Brave / Arc extension's score is structurally bounded by `breadth_max(30) + rule_modifier_cap(30) = 60` — HIGH band lower edge — when (a) no CVEs are available (browser extensions are not indexed in OSV today), (b) no `integration_sensitivity` table entry covers the extension's host surface, and (c) PID-join activity correlation is deferred to v0.3+. Empirical scan of this machine: the Claude Chrome extension lands at MEDIUM 41 (21 breadth + 20 max-rule from six dangerous-combo rules tied at max-wins) — the math is internally consistent; the apparent "should be CRITICAL" feel is the §6.4 transparency mandate working as designed. Path B for v0.3: introduce a `host_extension_surface` integration_sensitivity entry (~70) for `<all_urls> + nativeMessaging` extensions, which would land Claude ext at high-MEDIUM 55. Decision-log entry 2026-06-11.

### Fixed

- **Issue #98 follow-up — lifecycle hardening (task #181, 4 legs).** Closes a class of regression discovered on 2026-06-10 where four separate pytest invocations (running against the production proxy port) caused the user's running daemon to log 9 false-positive `orphan_mitmdump` crashes and silently disable the system proxy for ~2 hours.
  - **Leg 1 — `kill_orphan_mitmproxy` parent-PID liveness check.** New `lifecycle.is_child_of_running_monitor(pid)` helper walks up to the candidate's parent and verifies the parent is a live `ai-monitor --start` process. `find_orphan_mitmproxy_on_port` now skips any mitmdump whose parent is a live monitor, so concurrent `--start` invocations and stray pytest fixtures can no longer SIGTERM another monitor's healthy mitmdump child.
  - **Leg 2 — Watchdog symmetric system-proxy restore.** New `lifecycle.handle_mitmdump_death_and_restart(pm)` helper snapshots system-proxy state BEFORE disabling, restarts mitmdump, and re-enables the proxy iff it was on pre-disable. Counterpart `lifecycle.enable_system_proxy_for_port(port)` added. Capture no longer goes silently off after a watchdog cycle.
  - **Leg 3 — `--start` single-instance guard.** `lifecycle.is_monitor_already_running()` + `lifecycle.refuse_if_already_running()` check fresh-heartbeat + live PID file at the TOP of the `--start` path (BEFORE `detect_stale_state()`). Second invocation exits 1 with `ai-monitor is already running (PID N) — use --status / --restart` and never reaches the cleanup path.
  - **Leg 4 — Watchdog UX: surface mitmdump's actual exit reason.** `ProxyManager` now tracks `consecutive_restart_count` (resets on healthy streak) and captures `_last_exit_code`. After ≥2 consecutive restarts, the watchdog prints `mitmdump died (exit=N tail=...) — disabling system proxy` so the operator sees the real cause (`address already in use`, `confdir missing`, etc.) instead of the generic "died — restarted" message that historically masked real issues.
  - **Regression fixture.** `tests/test_lifecycle.py::TestParentMonitorOwnedMitmdumpIsNotOrphan`, `TestFindOrphanSkipsLiveMonitorChildren`, `TestStartRefusesWhenDaemonAlreadyRunning`, `TestProxyManagerExitReasonAfterRepeatedRestarts`, plus `tests/test_watchdog_explicit_stop.py::TestWatchdogRestoresSystemProxyOnRestart` — 15 new tests pin the regression on the 2026-06-10 crashes-table trace.

## [0.2.1] — 2026-06-03

### Fixed

- **Streaming response bodies from Anthropic Messages API are now correctly captured by the proxy addon (PR — issue #65).** Previously silently dropped due to a dispatch bug: the response hook used `raw.startswith("data:")` to decide between SSE and JSON parsers, which matched OpenAI SSE but missed Anthropic SSE (which leads with `event: message_start\n...`). The SSE parser was never reached for Anthropic streams; the JSON fallback raised `json.JSONDecodeError`; the bare `except: pass` silently swallowed the error. Affects all proxy-captured Claude Desktop, ChatGPT Desktop, Cursor, and streaming Claude Code sessions. Non-streaming responses were unaffected. The new dispatch uses `Content-Type: text/event-stream` as the canonical signal with a body-sniff fallback covering both `event:` (Anthropic) and `data:` (OpenAI) prefixes. The bare `except: pass` is replaced with a two-tier handler: expected parse failures log at WARNING; anything else logs at ERROR with full traceback. Historical rows with empty content cannot be backfilled.

- **`ai-monitor --status` capture matrix now reflects live evidence, not a static `sys_proxy` boolean.** Pre-fix the three desktop-AI-app rows (Claude Desktop / ChatGPT Desktop / Cursor) all printed `✅ Proxy (full capture)` whenever the user enabled system proxy, regardless of whether those apps were actually routing through the proxy or whether content was being decrypted. Ground-truth verification on 2026-06-01 proved this label was false — all three apps showed ✅ in `--status` while their chat messages produced zero captured rows. The replacement combines two live signals — does the app have an ESTABLISHED TCP connection to `127.0.0.1:9080`, and are there decrypted content rows (`input_tokens > 0`) from the app's expected host in the last hour — into one of four verdicts: `✅ Proxy verified — N rows captured last hour`, `⚠ Reaches proxy, no decrypted content (host may not be in allow_hosts)`, `❌ System proxy on but app routing direct (IPv6 / plugin-helper bypass)`, or `❌ Process only (system proxy disabled)`. The matrix now distinguishes Claude Desktop's IPv6 bypass (#70), ChatGPT Desktop's allow_hosts exclusion (#71), and Cursor's plugin-helper bypass with distinct, actionable labels.

- **Reverted IPv6 dual-stack listener change (PR #74 reverts PR #73) due to mitmproxy 12.x setting `IPV6_V6ONLY=1`, which made the IPv4 listener inaccessible.** PR #73 added `--listen-host ::` to the mitmdump cmdline on the assumption that macOS BSD default `IPV6_V6ONLY=0` would yield a single dual-stack socket. Empirical test on the installed mitmproxy 12.2.3 showed the assumption was wrong: mitmproxy 12.x explicitly sets `IPV6_V6ONLY=1` when an explicit listen host is passed, collapsing the bind to IPv6-only. macOS system proxy is always configured at an IPv4 host (`networksetup -setsecurewebproxy Wi-Fi 127.0.0.1 9080`), so all apps relying on system proxy got `Connection refused` after PR #73 merged. PR #74 restores the pre-PR-73 code; mitmproxy 12.x's default behaviour (no explicit `--listen-host`) binds BOTH IPv4 *:port and IPv6 *:port sockets, which is the working state. Issue #70 (Claude Desktop IPv6 bypass) remains open pending alternative approach — likely setting a second IPv6 system proxy via `networksetup` rather than changing the mitmproxy listener. A new empirical regression test in `tests/test_lifecycle.py::TestMitmdumpDualStackOnMacOS` runs a real mitmdump subprocess and asserts BOTH listeners are present; any future regression of this shape will fail at CI time instead of in production.

- **Response/request parsers now defend against non-dict JSON bodies.** Surfaced by the new ERROR-level logger added in the SSE dispatch fix above: `parse_response_body` was raising `AttributeError: 'NoneType' object has no attribute 'get'` when `json.loads(raw)` returned Python `None` (the body was the JSON literal `null`). All five JSON parsers (`parse_response_body`, `parse_openai_response`, `parse_google_response`, `parse_request_body`, `parse_openai_request`) now return the record unchanged when `body` is not a dict. Same defensive pattern across the response and request sides; the type annotation `body: dict` now matches runtime behaviour. Content fill rate for `/v1/messages` rows trended from 13% (pre-fix) to 82% (post-SSE-fix) and should climb further toward the legitimate ceiling with this guard in place.

- **README capture matrix and roadmap rewritten for accuracy.** Desktop AI app coverage (Claude Desktop, ChatGPT Desktop, Cursor) is documented with known limitations and the v0.3 architectural path forward (Apple Network Extension framework). Capture coverage claims match `--status` output verbatim (the four-verdict strings — `✅ JSONL + Proxy`, `⚠ Reaches proxy, no decrypted content (host may not be in allow_hosts)`, `❌ System proxy on but app routing direct (IPv6 / plugin-helper bypass)` — appear in the README's first-run "Expect" block character-for-character from `status.py`).
